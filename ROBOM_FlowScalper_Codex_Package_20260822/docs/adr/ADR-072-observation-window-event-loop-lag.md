# ADR-072 관찰 구간 기준 event-loop 지연 판정

## 상태

Accepted.

## 배경

Wave 95 최종 릴리스의 6시간 observer를 프로세스 시작 99초 뒤 실행했을 때 첫 표본의 queue는 148건이었고 `event_loop_lag_max_ms`는 이미 1,031ms였다. 이후 현재 처리·체결 지연과 queue가 정상이어도 이 필드는 프로세스 수명 전체의 최대값이라 줄어들지 않는다. 기존 observer는 모든 표본의 누적 최대값을 500ms 상한과 비교해 관찰 시작 전에 발생한 부팅 지연까지 새 6시간 실패로 다시 판정했다.

누적 최대값을 단순히 무시하면 관찰 중 새로 발생한 500ms 초과 지연을 놓칠 수 있다. 시작 직후 queue가 상한보다 큰 상태도 장시간 기준선으로 적합하지 않다.

## 결정

1. `SupervisorTelemetry`는 기존 프로세스 수명 최대값과 100ms 초과 계측을 보존한다.
2. 장시간 기본 gate와 같은 500ms를 초과한 event-loop scheduling 지연의 누적 횟수, 최근 발생시각과 최근 초과값을 별도로 기록한다.
3. 기본 500ms observer gate는 프로세스 수명 최대값이 아니라 관찰 마지막 횟수와 첫 표본 횟수의 증가분이 0인지 판정한다.
4. 500ms가 아닌 사용자 지정 상한은 기존 누적 최대값 판정을 유지한다. 임의 상한에 맞춘 사건 횟수를 런타임이 기록하지 않기 때문이다.
5. 100ms와 500ms 횟수는 모두 표본 사이에서 단조 증가해야 한다.
6. 증거에는 프로세스 수명 최대값과 관찰 중 500ms 초과 증가분을 함께 남겨 부팅 이력과 새 사건을 구분한다.
7. 새 장시간 관찰은 queue와 PAPER 안전 상태가 이미 등록 상한 안에 들어온 뒤 시작한다. 불안정한 첫 표본을 나중 정상값으로 평균내지 않는다.

## 결과

- 부팅 전후의 과거 1,031ms 최대값만으로 새 6시간이 거짓 실패하지 않는다.
- 관찰 시작 뒤 500ms 초과가 한 번이라도 발생하면 누적 횟수 증가로 실패한다.
- 고급진단에서 최근 초과값·시각·횟수를 직접 볼 수 있다.
- 기존 거래소 지연, critical lag, queue, 저장, 실제 주문 0과 인증 0 gate는 변경하지 않는다.
