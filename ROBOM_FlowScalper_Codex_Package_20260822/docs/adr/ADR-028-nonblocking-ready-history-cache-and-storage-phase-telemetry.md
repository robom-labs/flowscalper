# ADR-028. READY 비차단 과거통계와 저장 단계별 진단

## 상태

승인. 2026-08-25.

## 문제

활성 원장이 약 2GiB인 실제 macOS 서비스에서 `READY`를 만들 때 과거 main·shadow 거래를 동기식으로 읽었다. 실제 측정에서 PAPER 복구 조회는 약 0.9~2.4초였지만 과거 거래통계 준비가 차가운 파일 캐시에서 약 9.4~14.6초를 차지했다. 이 동안 첫 HTTP 응답이 늦어 사용자는 사이트가 닫혔거나 시작 버튼이 고장 난 것으로 볼 수 있었다.

또한 시장 이벤트 저장의 전체 소요시간만으로는 Parquet 작성, archive manifest 반영과 candle 원장 중 어느 단계가 느린지 구분할 수 없었다. 이벤트 수신 공백의 최댓값도 발생시각이 없어 저장 지연과 시간상 대조하기 어려웠다.

## 결정

1. PAPER 복구상태 조회와 checksum 검증은 서비스 준비 전에 계속 동기식으로 수행한다. 안전 복구를 빠른 화면 표시와 바꾸지 않는다.
2. `READY`의 과거 main·shadow 거래통계만 lifespan 백그라운드 thread에서 준비한다. 준비 중에도 `/api/status`, `/api/dashboard`와 시작 작업을 응답한다.
3. 과거통계의 준비완료, 로딩 중, 최근 소요시간과 완료시각을 시스템 고급진단에 표시한다.
4. 과거 main·shadow 조회는 SQLite WAL의 별도 query-only 연결을 사용한다. 긴 조회가 새 Run, PAPER 체결과 저장의 쓰기 잠금을 기다리게 하지 않는다.
5. LIVE·DEMO·REPLAY 런타임을 직접 구성하는 경로는 기존처럼 필요한 거래통계를 동기 준비해 결정성과 테스트 계약을 보존한다.
6. 저장 flush 최댓값이 갱신될 때 Parquet, manifest, candle 소요시간과 이벤트·candle·batch 수를 함께 보존한다.
7. 이벤트 수신 최대 공백의 발생시각을 보존하되 기존 1,500ms 신규진입 fail-closed 기준과 전략 임계값은 바꾸지 않는다.

## 결과

실제 서비스 측정에서 `READY` 런타임 내부 준비는 약 10.56초에서 0.212초로 줄었고 첫 재시작의 과거통계는 화면을 막지 않은 채 1.624초에 완료됐다. 다른 재시작에서는 저장장치 상태에 따라 동기 안전복구가 1.909초였지만 과거통계는 계속 백그라운드였다. 재시작 직후 실제 브라우저에서 시작을 누르면 250ms 안에 `연결 중`, 8초 뒤 `작동 중`이 표시됐다.

실제 LIVE 표본에서 한 저장 flush가 6.682초였을 때 Parquet 1.665초, manifest 1.642초, candle 3.365초였다. 같은 Run의 실행호가 지연 P95는 약 35ms였고 최대 이벤트 수신 공백은 1.047초, 비계획 재연결·시퀀스 갭·저장 실패는 0이었다. 따라서 이 표본은 외장 저장 I/O가 느렸다는 진단 증거이며 6시간·24시간 무지연 증거가 아니다.

전략, 비용, TP, SL, 위험예산, 실제주문 0과 private API 0 경계는 변경하지 않는다.
