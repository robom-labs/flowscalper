# ADR-025. 실시간 대시보드 통계 cache와 정밀분석 처리용량

## 상태

Accepted, 2026-08-25.

## 맥락

10개 전략과 BASE·STRESS 20개 독립계좌의 현재 구현버전 성과를 0.5초 WebSocket frame마다 전부 다시 집계했다. 저장된 현재버전 shadow 거래까지 매번 정규화하고 최근 50·100·300·전체 구간을 다시 계산했으며, 동시에 20개 deep 종목의 호가와 전략을 단일 Python 실행 루프에서 처리했다. 실제 서비스 무부하 관찰에서도 이벤트 지연 p95가 1,500ms를 넘어 안전잠금과 비계획 WebSocket 재연결이 재현됐다.

제품 요구사항은 넓게 50개 이상을 감시하고 기계와 연결 상태에 따라 8~12개를 정밀 분석하도록 정한다. 과거 deep 20 결정은 이후 전략 수가 10개와 양방향 20개 평가로 늘기 전 기준이므로 현재 처리용량과 맞지 않는다.

## 결정

1. wide 50개 감시는 유지하고 Binance·Bybit deep 구독 목표를 12개로 둔다. pin·진행·대기 PAPER 종목 보호와 회전 규칙은 유지한다.
2. 종목별 전략평가 500ms, 실제 호가별 PAPER 체결·TP·SL 관리, 신호·비용·위험 임계값은 바꾸지 않는다.
3. 현재 전략버전 성과는 과거 거래 수, 현재 Run, 각 독립계좌의 완료 거래 수와 마지막 거래 ID가 달라질 때만 다시 계산한다. 화면 frame 사이에는 같은 불변 report를 재사용한다.
4. 실행·진단용 최근 이벤트 10,000건은 유지한다. 대시보드 snapshot은 최신 512건만 투영하며 차트의 완성 candle, 스캐너의 최신 feature와 실제 계좌상태는 기존 전용 구조에서 가져온다.
5. 지연 p95가 1,500ms를 넘는 동안 PAPER 신규진입을 잠그는 fail-closed 기준은 그대로 유지한다.
6. 실제 주문, private API, API Key, 인증, secret과 wallet 경로는 계속 0이다.

## 검증

- 실제 supervisor 생성 시 두 공개 provider에 `deep_max=12`가 전달되는지 검사한다.
- LIVE 이벤트 1,000건 중 대시보드 투영이 최신 512건으로 제한되고 순서가 유지되는지 검사한다.
- 거래상태가 같으면 성과 집계가 한 번만 실행되고 Run 또는 완료 거래 상태가 바뀌면 다시 실행되는지 검사한다.
- 실제 서비스 재시작 뒤 브라우저 연결을 유지한 상태에서 dashboard 응답시간, 공개 이벤트 p50·p95, queue, critical, reconnect, drop, gap과 저장 fault를 연속 측정한다.

## 결과와 한계

처리용량 수정은 전략 기준을 낮추지 않고 실제로 정밀 계산할 수 있는 종목 수를 제품 요구범위 안으로 되돌린다. 짧은 정상 표본은 6시간·24시간 soak 또는 전략 수익성을 증명하지 않는다. 표본이 30건 미만인 전략은 계속 순위를 매기지 않는다.

macOS 자동 서비스는 archive worker process를 낮은 우선순위로 미리 기동하고, SQLite 실행 원장 반영은 이벤트 루프 밖 worker thread에서 수행하도록 보강했다. 실제 재시작 뒤 50 wide·12 deep과 10개 전략의 24개 경로 평가를 유지하면서 실행호가와 체결 p95는 보통 수십~수백 ms, queue·비계획 reconnect·gap·drop·persistence fault는 0이었다. wide scanner는 약 1.5~1.7초였으므로 실행호가와 분리한 ADR-026을 함께 적용했다. 이 실제 짧은 표본은 멀티시간 수용결과가 아니다.
