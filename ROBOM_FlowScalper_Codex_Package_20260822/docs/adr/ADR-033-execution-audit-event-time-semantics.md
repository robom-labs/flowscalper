# ADR-033. PAPER 실행 감사 이벤트의 실제 발생시각 보존

- 상태: Accepted
- 날짜: 2026-08-25
- 범위: PAPER 후보·진입·관리·청산 감사 원장 시각

## 배경

현재 Run의 독립 `LIVE_PUBLIC` 거래를 `shadow_trades`와 `execution_audit`에서 대조했다. 거래 원장의 `opened_ts_ms`, `closed_ts_ms`와 `holding_ms`는 14~54초 간격으로 정상이고 손익·비용 계산도 이 실제 시각을 사용했다. 그러나 같은 거래의 `ENTRY_FILLED`, `MANAGEMENT_EXIT_ARMED`, `EXIT_FILL` 감사 이벤트는 모두 후보의 `signal_time_ms`로 저장됐다. 이 때문에 감사 원장만 보면 진입과 청산이 동시에 일어난 것처럼 보였다.

직접 원인은 `PaperPortfolioEngine._audit()`가 이벤트 종류와 상관없이 항상 `plan.signal_time_ms`를 기록한 것이다. SQLite 저장기는 전달받은 `ts_ms`를 그대로 보존하므로 저장소나 손익 계산의 결함은 아니었다.

## 결정

1. 후보 평가·선택·계좌 배정처럼 신호 시점에 실제로 발생한 이벤트는 기존 `plan.signal_time_ms`를 유지한다.
2. 진입 만료·거절·미체결은 해당 도착 호가의 `book.ts_ms`를 기록한다.
3. `ENTRY_FILLED`는 실제 entry fill의 `book_ts_ms`를 기록한다.
4. 수동 종료와 전략 건강관리 종료 결정은 각각 요청·평가에 사용한 `now_ms`를 기록한다.
5. SL·TP·강제 종료 대기는 조건을 처음 관찰한 `book.ts_ms`를 기록한다.
6. 청산 거절·미체결은 시도한 호가의 `book.ts_ms`, `EXIT_FILL`은 실제 fill의 `book_ts_ms`를 기록한다.
7. `_audit()`에는 선택적인 `audit_ts_ms`만 추가하고, 전달하지 않은 후보 이벤트의 기존 의미는 바꾸지 않는다.
8. 과거 불변 원장은 수정하거나 재작성하지 않는다. 이 변경 전 감사 행은 당시 구현의 과거 기록으로 남기며, 새 Run과 구현 commit으로 이후 시각 의미를 구분한다.
9. 실제 주문, private API, API Key, secret과 wallet 경로는 계속 0으로 유지한다.

## 검증

회귀테스트는 후보 선택 1,000ms, 진입체결 1,250ms, TP1 대기·체결 2,000·2,250ms, TP2 대기·체결 3,000·3,250ms를 각각 구분한다. 별도 관리청산 시나리오는 결정 126,000ms와 실제 청산체결 126,250ms를 구분한다. 기존 후보·체결·Strategy League 회귀 75개와 전체 backend 322개를 함께 실행한다.

## 결과와 한계

- PAPER 거래의 계산값을 바꾸지 않고 원장·replay·화면 진단의 사건 순서만 실제 발생 순서와 일치시킨다.
- 변경 전 감사 행은 소급 보정하지 않으므로 과거 행을 분석할 때 거래 원장의 별도 진입·종료시각을 우선해야 한다.
- 자동테스트의 fixture 시각 분리는 구현 증거다. 실제 공개시장 새 Run에서 자연 진입과 종료가 발생한 뒤 persisted 감사 행까지 구분되는지는 별도 실행 증거로 기록한다.
- 이 수정은 전략 승률이나 수익성을 높였다는 증거가 아니다.
