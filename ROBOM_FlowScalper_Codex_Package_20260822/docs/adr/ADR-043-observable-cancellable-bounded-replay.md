# ADR-043 관찰 가능하고 취소 가능한 저장 Run 검증

- 상태: Accepted
- 일자: 2026-08-26
- 범위: 실제 공개시장 PAPER 서비스의 거래기록·과거재생·장시간 replay

## 문제

현재 Run의 거래 33건은 원장과 API에 있었지만, 공동계좌·현재 버전으로 한정된 화면과 긴 전략 버전 문구 때문에 없는 것처럼 보였다. 과거 재생 화면의 전략 검증은 HTTP 요청이 종료될 때까지 상태·경과시간·취소 수단을 내주지 않았다. 약 13만건 ZECUSDT 전체 재생이 25분 이상 계속되는 동안 실행경로 p95가 2.68초까지 상승하고 신규 진입이 안전 잠김되었다.

정밀 timeline은 화면이 2,000건만 요청해도 활성 SQLite 이벤트와 종목의 1초 candle 23,000개 이상을 먼저 검증했다. 실측 2,000건은 27.61초·5.04MB, 250건도 35.80초·3.81MB였다. 화면 담당 작업과 전체 전략 재검증의 비용 경계가 분리되지 않은 것이 원인이다.

## 결정

1. `POST /api/replay/{run_id}`는 202로 즉시 응답하고, `ReplayOperation` 상태를 `REQUESTED`, `PREPARING`, `PROCESSING`, `COMPLETED`, `FAILED_RETRYABLE`, `FAILED_BLOCKED`, `CANCELLING`, `CANCELLED`로 관리한다.
2. 동일 Run·종목 중복 요청은 같은 operation을 반환하고 다른 범위의 동시 요청은 409 `REPLAY_BUSY`로 즉시 알린다.
3. 상태 API와 DELETE 취소 API를 제공한다. 화면은 Run, 종목, 예상 이벤트, 경과시간, PAPER 안전 경계와 취소 버튼을 즉시 표시한다.
4. LIVE 재검증은 기존 `nice(19)`·한 CPU 코어 기준 5% 협력 예산을 유지하고, 취소 시 자식 process까지 종료한다. 서비스 종료도 활성 replay를 먼저 취소한다.
5. 과거 재생 진입은 Run 목록·최근 candle 미리보기를 전략 결과 전체 목록보다 먼저 표시한다. 결과 목록은 백그라운드에서 읽고 두 번째 요청부터 memory cache를 사용한다.
6. 화면 동기재생은 checksum 검증 이벤트 100건을 우선 읽는다. 전체 저장 건수는 따로 표시하고, 전체 전략 검증은 이 화면 상한과 무관하게 해당 종목의 저장 이벤트 전체를 사용한다.
7. 혼합 SQLite·Parquet 조회는 각 저장소에서 필요한 상한까지만 읽은 뒤 전체 정렬 키로 병합한다. candle은 선택된 이벤트의 첫·마지막 초 구간만 읽는다.
8. 거래 기록의 전략 버전은 내부 hash 전체를 반복 표시하지 않고 `현재 전략 버전`·`과거 전략 버전`으로 분류한다. 원장 값은 변경하지 않는다.

## 검증 경계

- 소형 실제 저장 Run `run-c74c67ff5976`의 ETHUSDT 125건을 전부 재검증해 전략평가 288회, 후보·거래 0, checksum `636bf7f3162147d3db559a0080660d44db9e9551d6df330378899dadd243bf1a`를 확인했다.
- 현재 대형 Run은 모바일 화면에서 상태 패널을 354ms 만에 표시했고, 취소 후 `CANCELLING`→`CANCELLED`로 종료되었다.
- 현재 ZECUSDT 화면 timeline 100건은 0.63초·75KB였고 candle 17개만 포함했다. 2,000건 직접 API의 전체 응답은 여전히 27.61초이므로 전문 진단 범위로 남긴다.
- 전략 임계값, 비용, TP/SL, ACTIVE/SHADOW/OFF는 변경하지 않았다. 30건 미만 전략을 순위화하지 않고 수익성은 `NOT_PROVEN`으로 유지한다.
- 활성 2.55GB 원장 전수 `quick_check`는 작동 중 writer와의 경쟁을 피하기 위해 이 Wave에서 재실행하지 않는다. Wave34의 전수 PASS를 이번 실행 PASS로 재표현하지 않는다.
