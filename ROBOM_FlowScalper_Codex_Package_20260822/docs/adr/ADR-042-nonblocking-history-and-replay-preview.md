# ADR-042. 비차단 거래기록 cache와 replay 미리보기 분리

- 상태는 Accepted다.
- 날짜는 2026-08-26이다.

## 배경

활성 2.3GB SQLite 원장의 거래기록 API가 화면 요청마다 main·전략리그 전체 거래를 다시 검증해 전체 범위 조회에 6.24초가 걸렸다. 거래기록 화면 기본값은 공동계좌만 선택해 현재 Run의 전략별 PAPER 거래 22건이 있어도 빈 표를 표시했다. 로딩 상태가 없어 사용자는 데이터가 없는 것과 아직 읽는 중인 상태를 구분할 수 없었다.

과거 재생 화면은 Run 목록을 연 직후 선택한 종목의 checksum 검증 이벤트 2,000개를 자동으로 읽었다. 현재 대형 Run에서 이 요청은 37.52초가 걸렸고, 선택기와 차트가 그동안 비어 있으며 공개시장 처리와 저장 I/O에도 불필요한 경쟁을 만들었다.

첫 수정 뒤 실제 저장 checkpoint와 겹친 후속 점검에서 거래기록과 Run 목록이 다시 15~20초 제한을 넘겼다. 거래행의 `replay_available` 계산과 `/api/replay/runs`가 `list_replayable_run_summaries()`를 요청마다 호출해 활성 SQLite read connection과 경쟁한 것이 남은 원인이었다.

## 결정

1. LIVE 거래기록은 런타임 시작 때 checksum 검증한 main·전략리그 전체 거래 cache와 현재 메모리 완료 거래를 `trade_id`로 병합한다.
2. Replay와 비LIVE 모드는 기존처럼 불변 원장을 직접 읽는다. cache와 원장 범위·필터 의미는 동일해야 한다.
3. 거래기록 기본 계좌 범위는 공동계좌와 전략별 계좌를 모두 포함한다. 공동·전략별 건수를 별도로 표시하고 5초마다 비차단 갱신한다.
4. 거래기록 로딩·실패·실제 0건을 서로 다른 한국어 상태로 표시한다.
5. replay 첫 화면과 Run·종목 변경은 종목 통계와 최근 1초 candle 최대 500개만 읽는 빠른 미리보기를 사용한다. 대용량 Parquet 이벤트 본문은 읽지 않는다.
6. checksum 검증 정밀 이벤트 로딩과 동일 전략 파이프라인 재검증은 별도 버튼으로 분리한다. 전략 재검증은 정밀 이벤트가 준비된 뒤에만 허용한다.
7. Run 변경 순간 이전 Run의 종목·timeline을 비워 교차 Run 요청을 차단한다.
8. replay checksum, archive 검증, 5% CPU 예산, 동시 replay 잠금과 PAPER 안전기준은 변경하지 않는다.
9. 거래가 적다는 이유로 전략 임계값, 비용, 손익비 또는 자연신호 조건을 낮추지 않는다.
10. LIVE의 replay Run 요약도 시작 시 검증 cache에 넣고, 현재 세션의 성공한 저장 batch와 아직 저장 전 buffer 개수를 증분 합산한다. 거래기록과 Run 목록은 cache 준비 뒤 활성 SQLite를 다시 읽지 않는다.

## 결과

- 현재 Run 거래기록 5회 반복 조회는 22.8~34.3ms였고 공동계좌 0건·전략별 계좌 22건을 표시했다.
- 현재 Run 최근 candle 500개 미리보기는 199ms였고 이벤트 0개를 읽었다.
- 실제 브라우저에서 소형 저장 Run의 정밀 이벤트 24개는 631ms, 동일 조건 전략 검증은 1.95초에 완료됐다.
- 대형 Run을 화면에 여는 것만으로 정밀 이벤트 scan이나 전략 replay가 시작되지 않는다.
- 저장 checkpoint와 겹쳐 15~20초를 넘긴 재현 뒤 서비스에 적용한 12회 연속 측정에서 거래기록은 9.8~30.8ms, Run 목록은 2.5~19.2ms였고 모두 HTTP 200이었다.
- 실제 브라우저 후속 점검에서 현재 거래기록 28건, 저장 Run 79개, 소형 Run 최근 candle 24개, 정밀 이벤트 24개와 동일 조건 전략검증 완료를 확인했고 콘솔 오류는 0이었다.
- 현재 자연표본은 비용후 음수이고 30건 미만이므로 수익성은 `NOT_PROVEN`이다.

## 기각한 대안

- 거래가 보이도록 공동계좌에 전략리그 거래를 복사하면 계좌 격리와 원장 진실성을 깨므로 기각했다.
- Parquet checksum을 생략하거나 샘플 row만 읽는 방식은 손상 탐지를 약화하므로 기각했다.
- 전략 신호 기준을 낮춰 거래 수를 늘리는 방식은 과매매와 선택 편향을 만들므로 기각했다.
- 대형 timeline을 계속 자동 실행하면서 spinner만 추가하는 방식은 LIVE 처리 경쟁을 제거하지 못해 기각했다.

## 검증 계약

- LIVE cache 준비 뒤 거래기록 API가 활성 원장의 전체 거래 목록을 다시 읽지 않는 단위검사.
- LIVE cache 준비 뒤 거래기록과 replay Run 목록이 활성 원장의 Run 요약을 다시 읽지 않고, 저장 전 buffer와 성공한 저장 batch를 중복 없이 합산하는 단위검사.
- main·전략리그·Run·비용·버전·sample type 필터 의미 회귀검사.
- replay 페이지가 preview만 자동 호출하고 timeline은 버튼 전에는 호출하지 않는 UI 검사.
- Run 변경 직후 이전 종목이 새 Run 요청에 사용되지 않는 실제 브라우저 검사.
- 전체 backend, frontend, 정적검사, PAPER safety, security, 저장소 위생, desktop·tablet·mobile E2E.
- 실제 서비스의 기록·preview·정밀 이벤트·전략 검증 버튼과 후속 공개시장 처리 상태 확인.
