# ADR-020. 단조시각 기반 거래소 지연과 계획 교체 복구

## 상태

Accepted — 2026-08-25.

## 문제

`run-94899287d623`의 첫 연결에서는 Binance 공개 시각과 로컬 시각 차이가 약 +2.1초였고, 기존 구현은 이 값을 Run의 다음 계획 교체 때까지 고정했다. 실행 중 macOS wall clock이 보정된 뒤 실제 차이는 약 +64ms가 됐지만 기존 +2,158ms를 계속 더해 정상 공개 이벤트가 2초 이상 늦은 것으로 계산됐다. 실행경로 p50 2,120ms·p95 2,321ms, 임계지연 누계 19,804와 신규 PAPER 진입 안전잠금이 발생했다. 안전잠금 자체는 올바르게 작동했지만 지연 입력이 잘못됐다.

짧은 주기의 실제 공개 WebSocket 검증에서는 세 연결의 기본 close timeout이 순차 적용돼 계획 교체가 30초 표본 안에 끝나지 않는 정지 구간도 확인됐다. 또한 기존 스트림이 끝난 뒤 새 metadata와 depth snapshot을 준비하는 동안 재연결·진입잠금 표시가 늦게 바뀌었다.

## 결정

1. Binance와 Bybit 공개 시각은 세 표본 중 monotonic RTT가 가장 작은 응답으로 보정한다.
2. 선택한 서버 timestamp를 응답의 monotonic 중간점에 고정하고 이후 거래소 현재시각은 monotonic 경과시간으로 계산한다. 운영체제 wall clock이 앞뒤로 바뀌어도 이벤트 지연은 이 기준에서 계산한다.
3. 화면에 표시하는 거래소·로컬 오프셋은 고정 측정값이 아니라 현재 wall clock과 monotonic 거래소 시각의 차이로 계속 갱신한다. 운영체제 시각 자체는 수정하지 않는다.
4. 구형 fixture와 기록 공급자는 calibration이 없으면 기존 `local + offset - venue timestamp` 계산을 유지한다.
5. Binance wide·depth·trade와 Bybit 공개 WebSocket의 종료 대기는 연결당 1초로 제한한다. 정상 교체 뒤 새 sequence-valid depth가 오기 전까지 신규 PAPER 진입을 잠근다.
6. 계획 교체를 감지한 즉시 상태를 `RECONNECTING`으로 바꾸고 새 metadata 준비 전에 진입잠금을 설정한다. 새 정상 depth를 관찰한 뒤에만 `LIVE`와 진입 허용으로 복구한다.
7. 비계획 연결 오류도 backoff 뒤 기존 시각 보정을 재사용하지 않고 공개 metadata와 거래소 시각을 다시 검증한다. 재검증 실패는 같은 fail-closed 재시도 경로에 남는다.
8. 실제 주문, private API, 인증, API Key, secret과 wallet 경로는 추가하지 않는다.

## 검증

- 결정적 시계가 wall clock만 +2초 이동해도 monotonic 거래소 지연이 0ms를 유지하고 표시 오프셋만 +2,000ms에서 +10ms로 바뀌는지 검사한다.
- 계획 교체의 두 번째 `prepare()`를 의도적으로 막아, 준비가 끝나기 전 `RECONNECTING`과 진입잠금이 이미 적용됐는지 검사한다.
- 실제 Binance 공개 스트림 12개 wide·10개 deep을 6초 주기로 교체해 세 번 모두 새 이벤트와 진입 허용으로 자동 복구되는지 측정한다.
- 서비스 재시작 뒤 실제 브라우저에서 한 번의 시작 클릭이 `시작 전 → 연결 중 → 작동 중`으로 전환되는지 확인한다.
- 전체 backend·frontend·Playwright·정적·보안 검사를 다시 실행하고 실제 서비스 지연·queue·drop·gap·오류가 부하 뒤 정상인지 확인한다.

2026-08-25 실제 단축 교체 검증은 계획 교체 3회와 복구 3회를 완료했고 복구시간은 최대 0.919초였다. 최종 deep p50 20.535ms·p95 22.851ms, 비계획 재연결·임계지연·진입잠금·drop·gap은 0이었다. 이 단축 검증은 동일 생산 provider 코드의 교체 경로 증거지만 6시간·24시간 soak나 인터넷 품질을 일반적으로 보장하지 않는다.

같은 날 실제 서비스의 생산 기본 900초 교체도 1회 관찰했다. 교체 시작 즉시 `RECONNECTING`·진입잠금이 보였고 1.749초 뒤 fresh depth·`LIVE`·진입 허용으로 복구됐다. 교체 뒤 비계획 재연결·drop·gap·error는 0이었다. 교체 전에 발생한 임계지연 406건은 저장 이벤트상 별도의 43.418초 구간에 있었고 교체 뒤 40초 표본과 최종 backend 회귀검사 뒤 후속 187,574 event까지 증가하지 않았다. 이 실제 지연은 fail-closed로 차단·자동복구됐지만 당시 경쟁 프로세스의 정확한 원인은 Parquet만으로 특정하지 않는다.

## 결과와 한계

wall clock 보정은 더 이상 실행경로 지연을 거짓으로 높이지 않는다. 실제 네트워크 지연, CPU 정체와 오래된 venue timestamp는 기존 1,500ms fail-closed 기준으로 계속 신규 PAPER 진입을 잠근다. 계획 교체 중 잠깐의 진입잠금은 정상이며 시장 관찰은 새 검증 이벤트 뒤 자동 복귀한다. 충분한 장시간 검증과 전략 수익성은 별도 증거가 필요하다.
