# ADR-106. 거래 집중 재생의 요청 격리와 검증된 메모리 캐시

- 상태. 채택.
- 일자. 2026-08-30.
- 범위. 저장된 공개시장 PAPER 거래 한 건의 읽기 전용 집중 재생만 해당한다.

## 배경

큰 활성 원장에서 선택 거래의 캔들·이벤트·계획·체결을 처음 조합하면 수십 초가 걸릴 수 있다. 이때 사용자가 거래를 바꾸거나 화면을 닫아도 이전 요청이 뒤늦게 상태를 덮거나, 선택적 SQLite 캐시 쓰기가 LIVE 원장 writer의 잠금을 기다리면 거래기록과 전략통계까지 느려 보일 수 있었다. 집중 재생 결과의 본체는 불변 원장 읽기이며 cache는 선택적 가속 계층이다.

## 결정

1. 프론트엔드는 거래 집중 요청마다 `AbortController`를 만들고 선택 거래가 바뀌거나 화면이 닫히면 이전 요청을 취소한다. 취소된 응답은 화면 상태를 갱신하지 않는다.
2. `SQLiteLedger`는 일반 분석 읽기 연결과 별도로 query-only 집중 재생 연결과 lock을 가진다. 일반 읽기 lock을 즉시 얻을 수 있을 때만 공유하고, 아니면 전용 연결에서 정확한 cache key를 읽는다.
3. 프로세스 시작 때 저장된 `replay_focus_cache`를 메모리에 올리고, `(Run, trade, profile, session_version)` 키로 먼저 조회한다.
4. 메모리와 SQLite 결과는 같은 zlib payload와 SHA-256 checksum 검증을 통과해야 반환한다. 압축 손상, checksum 불일치와 객체가 아닌 payload는 원장 불변조건 오류다.
5. 첫 세션을 만든 뒤 선택적 SQLite cache 쓰기가 `locked` 또는 `busy`면 차트 결과를 실패시키지 않는다. 완성 세션을 checksum과 함께 현재 프로세스 메모리에 보존해 같은 요청을 다시 계산하지 않는다.
6. 전략 신호, 체결, 비용, 거래금액, TP·SL, replay checksum과 원장행은 변경하지 않는다.

## 검증 경계

- 큰 실제 원장의 첫 미보유 거래 집중 세션은 27.541초에 만들어졌다. 같은 프로세스의 반복 조회 여섯 번은 4.3~28.6ms였다.
- 실제 브라우저에서 진입 77,910.1, TP1 78,272.46, SL 77,676.32와 실제 종료 78,016.1을 각각 눌러 같은 저장 거래의 프레임을 확인했다.
- 이 결과는 선택 거래 재생의 정확성과 반복 응답 가속 증거다. 전체 대형 Run 전략 replay 완료, 6시간·24시간 안정성 또는 수익성을 증명하지 않는다.
